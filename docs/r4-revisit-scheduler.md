## Ordering and capacity

The queue orders by deadline, target, then mint. A mint needs at most one targeted request at a time; a request can close multiple references only when it starts after each reference's target and Jupiter evidence is post-target for each. Each entry is checked against its own deadline and source evidence. Due, Jupiter-ready targets run before passive round-robin Dex work. The provider exposes remaining requests, its actual rolling-window reset, transport spacing and backoff, and busy state. No fixed `pollMs` deferral is applied after a budget denial. The planner reserves a slot for every pending reference targeting the current provider window, conservatively allowing for same-mint references that cannot coalesce. Passive work uses only unreserved capacity and resumes after target pressure clears.

The latest safe start is `target + 60,000 ms - (Dex HTTP timeout + Dex request spacing + 5,000 ms)`. At default configuration this is target +45,800 ms. The extra five seconds is an engineering allowance for Jupiter copies, response normalization, durable recorder writes, and snapshot construction. The recorder checks this cutoff immediately before each targeted request. A late start is a deadline miss; a snapshot after the hard deadline is a deadline miss even if the request started in time. This allowance is not a claim that disk latency is absolutely bounded: actual snapshot time is authoritative for the deadline result.

## Telemetry and replay

`revisit-scheduler.ndjson` contains structural queue and timing events: target/deadline, queue depth, request start/receipt, snapshot time, queue lag, coalesced count, result and failure code. Storage hashes it in the session manifest. The production reader authenticates and checks its schema when present, while accepting older sessions without the file. It does not use this telemetry for price or outcome resolution.

The offline replay reads the authenticated shakedown reference structure and Jupiter provider observation times. It uses the configured six-request/30-second Dex window, two passive requests per ordinary capture, 39-second ordinary cadence, and 1.2-second serialized requests. It does not read prices or calculate returns. This is a deterministic capacity model, not a substitute for a second bounded live shakedown.
